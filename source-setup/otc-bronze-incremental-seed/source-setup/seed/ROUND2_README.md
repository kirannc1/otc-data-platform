# Bronze round-two incremental source seed

This fixture adds a small set of order-to-cash transactions to the existing **demo** sources. The four Bronze DAGs can then show the difference between full snapshots, manifest-driven file delivery, and Kafka offsets. Use the existing source environment, company, items, customers, accounts, and warehouses.

## What the script adds

The new commercial transactions are dated **15 November 2026**. Each company invoices two pumps at **₹10,000 per unit**, applies a **₹10,000 partial credit**, and has **₹10,000 open receivables** on the new invoice. The credit is a financial allowance. Both pumps remain shipped. The fixture creates no payment for either invoice. There is also a separate parent counter sale for testing POS ingestion.

| Source | New records and identifiers | Purpose |
|---|---|---|
| Parent ERPNext | `P-BRONZE-R2-STOCK`, `P-BRONZE-R2-ORDER`, `P-BRONZE-R2-SHIP`, `P-BRONZE-R2-INVOICE`, `P-BRONZE-R2-CREDIT` | Reuse the customer, pump and warehouse from `P-S1`. Receive two extra pumps at ₹6,000 cost each, book and ship both, post a ₹20,000 invoice and allocate the ₹10,000 credit against it. |
| Parent ERPNext GL | Posting lines generated by ERPNext when the documents are submitted | Verify that invoice and credit vouchers balance, that AR moves by +₹20,000 then −₹10,000, and that the sales account posts ₹10,000 net revenue. Stock and delivery GL line counts can vary with ERP configuration. |
| Dealer PostgreSQL | `D-BRONZE-R2-ORDER`, one line, one shipment, one storefront order and acceptance, one invoice, one credit, one AR snapshot and four GL lines | Reuse `D-C1`, `D-PUMP` and `D-WH1`. The new invoice and credit share the order key. The dealer schema carries the credit as an invoice row with `document_type=credit_note` and a negative amount. The AR snapshot points to the invoice. |
| Parent Commerce | `P-BRONZE-R2-EVENT` for the new ERP order reference and separate POS receipt `P-BRONZE-R2-POS` | The existing outbox publishes the acceptance to `parent.orders.v1`. The POS API provides a distinct ₹10,000 card sale for the REST DAG. |
| Source MinIO | New dealer export manifest and CSV files, published by the existing export Job | The dealer export includes the new billing, AR, storefront and GL records. It is a full delivery, so its CSVs also contain existing rows. |

ERPNext assigns its own document numbers. The script prints them along with the round-two reference and the verified invoice and credit GL identifiers. The Commerce event timestamp comes from the API at acceptance. The dealer simulator stores amounts in integer paise, so ₹20,000 is `2000000`.

### Accounting entries for each new invoice and credit

| Voucher | Debit | Credit |
|---|---|---|
| Invoice | Accounts receivable ₹20,000 | Sales revenue ₹20,000 |
| Partial credit | Sales revenue ₹10,000 | Accounts receivable ₹10,000 |

## 1. Capture the unchanged Bronze baseline

Before posting anything, trigger all four Bronze DAGs on the **platform machine** and note their run IDs. Keep the new REST and SQL manifests for comparison. Files should report zero new deliveries if the upstream manifests were unchanged. Kafka should report zero deliveries if its group had caught up.

## 2. Prepare and preflight the seed

Extract this ZIP into the repository root on the **source machine**. It adds this guide and `source-setup/seed/otc_bronze_seed_round2.py`. Reuse the existing seed virtual environment and `source-setup/seed/erp.env` from the first seed. The ERP demo company needs an open fiscal period for 15 November 2026 and API access to create, submit, and read back the documents. The seed will use the existing tax-free demo configuration.

In separate PowerShell windows on the source machine, keep your working local forwards for ERPNext, Commerce and PostgreSQL open. The documented defaults are:

```powershell
kubectl --context kind-otc -n otc-erp port-forward svc/erpnext 18080:8080
kubectl --context kind-otc -n otc-sources port-forward svc/commerce 8000:8000
kubectl --context kind-otc -n otc-sources port-forward svc/postgres 15432:5432
```

From the repository root, in the PowerShell window that will run the seed, reuse the first-seed `DEALER_SEED_DSN` or set it as follows. Use the dealer database writer identity. The Airflow reader account is for ingestion.

```powershell
$Python = '.\.venv\Scripts\python.exe'
$Script = '.\source-setup\seed\otc_bronze_seed_round2.py'
$Encoded = kubectl --context kind-otc -n otc-sources get secret source-credentials -o 'jsonpath={.data.POSTGRES_PASSWORD}'
if ($LASTEXITCODE -ne 0 -or -not $Encoded) { throw 'Could not read the PostgreSQL credential.' }
$Password = [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($Encoded))
$DbPassword = [Uri]::EscapeDataString($Password)
$env:DEALER_SEED_DSN = "postgresql://postgres:${DbPassword}@127.0.0.1:15432/dealer_legacy"
$env:COMMERCE_URL = 'http://127.0.0.1:8000'
Remove-Variable Encoded, Password, DbPassword
& $Python $Script
if ($LASTEXITCODE -ne 0) { throw 'Round-two preflight failed.' }
```

Preflight checks the ERP configuration and existence of parent order `P-S1`, the Commerce health endpoint, and the seeded dealer order and accounts. It makes no source writes. It does not submit a test ERP document, so posting rules are evaluated at apply time. Values already set in the process environment take precedence over `erp.env`.

## 3. Apply the seed and publish the dealer export

```powershell
& $Python $Script --apply
if ($LASTEXITCODE -ne 0) { throw 'Round-two seed failed. Check the reported source step before retrying.' }

$ExportJob = "dealer-export-r2-$(Get-Date -Format 'yyyyMMddHHmmssfff')"
kubectl --context kind-otc -n otc-sources create job --from=cronjob/dealer-export $ExportJob
if ($LASTEXITCODE -ne 0) { throw 'Dealer export Job creation failed.' }
kubectl --context kind-otc -n otc-sources wait --for=condition=complete "job/$ExportJob" --timeout=180s
if ($LASTEXITCODE -ne 0) { throw "Dealer export did not complete: $ExportJob" }
kubectl --context kind-otc -n otc-sources logs "job/$ExportJob"
if ($LASTEXITCODE -ne 0) { throw 'Could not confirm the dealer export manifest.' }
```

The three source writes are independent. ERPNext submits documents one at a time and reuses stable references. Dealer rows commit together and an existing row must match the fixture. Commerce reuses the same event and receipt IDs on retry. If a step fails partway, fix the reported issue and rerun with the same IDs. If ERPNext leaves the credit unallocated, inspect the original new invoice and the existing credit in Payment Reconciliation. Apply the existing credit to the new invoice, then rerun the script to verify outstanding AR and continue.

Run the export Job once per test delivery. A new Job and snapshot ID create another file delivery even when the underlying business data is unchanged. Make sure the Commerce outbox has published the event before validating Kafka. You can confirm from the source machine with:

```powershell
@'
from main import connect

with connect() as db:
    row = db.execute(
        "SELECT published FROM outbox WHERE event_id=%s",
        ("P-BRONZE-R2-EVENT",),
    ).fetchone()
print(row)
raise SystemExit(0 if row == (True,) else 1)
'@ | kubectl --context kind-otc -n otc-sources exec -i deploy/outbox -- python -
if ($LASTEXITCODE -ne 0) { throw 'Round-two Kafka event is not marked published yet.' }
```

## 4. Verify in Bronze and in VS Code

Trigger all four Bronze DAGs again after the seed and export finish. Compare against the unchanged baseline.

| DAG | Expected result with the new fixture |
|---|---|
| `otc_bronze_rest` | Parent ERP full snapshot adds one Sales Order, one Stock Entry, one Delivery Note, two Sales Invoice documents and the generated GL lines. Parent POS adds one receipt. |
| `otc_bronze_sql` | Dealer full snapshot adds one row each to `sales_orders`, `order_lines`, and `shipments`. Customer, product, account and warehouse counts stay the same. |
| `otc_bronze_files` | One new logical dealer delivery if only the round-two export ran. In its manifest, `invoices` has two more rows, `receivables` one more row, and `gl_entries` four more rows than the baseline export. |
| `otc_bronze_kafka` | Expect one logical acceptance with event ID `P-BRONZE-R2-EVENT`. Each Kafka delivery has its own partition and offset. |

In the first Silver discovery notebook, **Open the actual records** shows a DataFrame. Use `source = "erpnext"` and `collection = "Sales Invoice"` for the invoice and credit. Use `collection = "GL Entry"` for voucher postings. With `source = "dealer-sql"`, use `collection = "sales_orders"` or `"shipments"`. For dealer billing and GL, select the exact CSV object key from the newly published export in `inventory_df`.

For a final unchanged rerun, leave the sources and export schedule quiet. REST and SQL publish new run snapshots. Files have no new delivery to copy, and Kafka has no new events once caught up. Compare row counts and checksums by collection across the two committed snapshots.
